# Willow Service

## Overview

The Willow service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Willow exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Willow v2.2.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Willow.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_WILLOW_TIMEOUT_MS (default 3550)
- NIMBUS_WILLOW_MAX_RETRIES (default 5)
- NIMBUS_WILLOW_POOL_SIZE (default 40)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_WILLOW_TIMEOUT_MS affects request timeout behavior for Willow.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/willow/restart
- GET /api/v1/willow/status
- POST /api/v1/willow/cache/flush
Use POST /api/v1/willow/restart to restart the Willow service, GET /api/v1/willow/status to check health, and POST /api/v1/willow/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Willow service:
- ERR-1221: connection pool exhausted
- ERR-1222: upstream timeout exceeded
- ERR-1223: invalid authentication token
- ERR-1224: payload schema validation failed
When you see ERR-1221, the connection pool is exhausted; increase NIMBUS_WILLOW_POOL_SIZE. ERR-1222 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Willow service. If you observe connection drops or high latency, first check GET /api/v1/willow/status, then review recent error codes. Restart with `nimbusctl willow restart` or POST /api/v1/willow/restart. Persistent timeouts usually mean NIMBUS_WILLOW_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
