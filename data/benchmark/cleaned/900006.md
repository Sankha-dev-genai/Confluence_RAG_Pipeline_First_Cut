# Flint Service

## Overview

The Flint service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Flint exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Flint v3.5.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Flint.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_FLINT_TIMEOUT_MS (default 3125)
- NIMBUS_FLINT_MAX_RETRIES (default 4)
- NIMBUS_FLINT_POOL_SIZE (default 36)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_FLINT_TIMEOUT_MS affects request timeout behavior for Flint.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/flint/restart
- GET /api/v1/flint/status
- POST /api/v1/flint/cache/flush
Use POST /api/v1/flint/restart to restart the Flint service, GET /api/v1/flint/status to check health, and POST /api/v1/flint/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Flint service:
- ERR-1051: connection pool exhausted
- ERR-1052: upstream timeout exceeded
- ERR-1053: invalid authentication token
- ERR-1054: payload schema validation failed
When you see ERR-1051, the connection pool is exhausted; increase NIMBUS_FLINT_POOL_SIZE. ERR-1052 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Flint service. If you observe connection drops or high latency, first check GET /api/v1/flint/status, then review recent error codes. Restart with `nimbusctl flint restart` or POST /api/v1/flint/restart. Persistent timeouts usually mean NIMBUS_FLINT_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
