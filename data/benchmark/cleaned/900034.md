# Harbor Service

## Overview

The Harbor service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Harbor exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Harbor v1.3.0. Owner: Data Team. This document describes configuration, endpoints, error codes, and troubleshooting for Harbor.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_HARBOR_TIMEOUT_MS (default 3825)
- NIMBUS_HARBOR_MAX_RETRIES (default 4)
- NIMBUS_HARBOR_POOL_SIZE (default 20)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_HARBOR_TIMEOUT_MS affects request timeout behavior for Harbor.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/harbor/restart
- GET /api/v1/harbor/status
- POST /api/v1/harbor/cache/flush
Use POST /api/v1/harbor/restart to restart the Harbor service, GET /api/v1/harbor/status to check health, and POST /api/v1/harbor/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Harbor service:
- ERR-1331: connection pool exhausted
- ERR-1332: upstream timeout exceeded
- ERR-1333: invalid authentication token
- ERR-1334: payload schema validation failed
When you see ERR-1331, the connection pool is exhausted; increase NIMBUS_HARBOR_POOL_SIZE. ERR-1332 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Harbor service. If you observe connection drops or high latency, first check GET /api/v1/harbor/status, then review recent error codes. Restart with `nimbusctl harbor restart` or POST /api/v1/harbor/restart. Persistent timeouts usually mean NIMBUS_HARBOR_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Data Team.
