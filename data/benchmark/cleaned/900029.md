# Cinder Service

## Overview

The Cinder service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Cinder exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Cinder v2.8.0. Owner: Data Team. This document describes configuration, endpoints, error codes, and troubleshooting for Cinder.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_CINDER_TIMEOUT_MS (default 3700)
- NIMBUS_CINDER_MAX_RETRIES (default 3)
- NIMBUS_CINDER_POOL_SIZE (default 32)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_CINDER_TIMEOUT_MS affects request timeout behavior for Cinder.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/cinder/restart
- GET /api/v1/cinder/status
- POST /api/v1/cinder/cache/flush
Use POST /api/v1/cinder/restart to restart the Cinder service, GET /api/v1/cinder/status to check health, and POST /api/v1/cinder/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Cinder service:
- ERR-1281: connection pool exhausted
- ERR-1282: upstream timeout exceeded
- ERR-1283: invalid authentication token
- ERR-1284: payload schema validation failed
When you see ERR-1281, the connection pool is exhausted; increase NIMBUS_CINDER_POOL_SIZE. ERR-1282 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Cinder service. If you observe connection drops or high latency, first check GET /api/v1/cinder/status, then review recent error codes. Restart with `nimbusctl cinder restart` or POST /api/v1/cinder/restart. Persistent timeouts usually mean NIMBUS_CINDER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Data Team.
