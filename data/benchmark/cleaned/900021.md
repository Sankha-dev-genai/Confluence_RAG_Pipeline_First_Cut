# Umber Service

## Overview

The Umber service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Umber exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Umber v3.0.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Umber.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_UMBER_TIMEOUT_MS (default 3500)
- NIMBUS_UMBER_MAX_RETRIES (default 3)
- NIMBUS_UMBER_POOL_SIZE (default 32)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_UMBER_TIMEOUT_MS affects request timeout behavior for Umber.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/umber/restart
- GET /api/v1/umber/status
- POST /api/v1/umber/cache/flush
Use POST /api/v1/umber/restart to restart the Umber service, GET /api/v1/umber/status to check health, and POST /api/v1/umber/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Umber service:
- ERR-1201: connection pool exhausted
- ERR-1202: upstream timeout exceeded
- ERR-1203: invalid authentication token
- ERR-1204: payload schema validation failed
When you see ERR-1201, the connection pool is exhausted; increase NIMBUS_UMBER_POOL_SIZE. ERR-1202 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Umber service. If you observe connection drops or high latency, first check GET /api/v1/umber/status, then review recent error codes. Restart with `nimbusctl umber restart` or POST /api/v1/umber/restart. Persistent timeouts usually mean NIMBUS_UMBER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
