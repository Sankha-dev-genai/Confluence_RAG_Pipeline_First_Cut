# Halite Service

## Overview

The Halite service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Halite exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Halite v2.7.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Halite.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_HALITE_TIMEOUT_MS (default 3175)
- NIMBUS_HALITE_MAX_RETRIES (default 6)
- NIMBUS_HALITE_POOL_SIZE (default 44)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_HALITE_TIMEOUT_MS affects request timeout behavior for Halite.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/halite/restart
- GET /api/v1/halite/status
- POST /api/v1/halite/cache/flush
Use POST /api/v1/halite/restart to restart the Halite service, GET /api/v1/halite/status to check health, and POST /api/v1/halite/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Halite service:
- ERR-1071: connection pool exhausted
- ERR-1072: upstream timeout exceeded
- ERR-1073: invalid authentication token
- ERR-1074: payload schema validation failed
When you see ERR-1071, the connection pool is exhausted; increase NIMBUS_HALITE_POOL_SIZE. ERR-1072 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Halite service. If you observe connection drops or high latency, first check GET /api/v1/halite/status, then review recent error codes. Restart with `nimbusctl halite restart` or POST /api/v1/halite/restart. Persistent timeouts usually mean NIMBUS_HALITE_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
