# Aurora Service

## Overview

The Aurora service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Aurora exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Aurora v1.0.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Aurora.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_AURORA_TIMEOUT_MS (default 3000)
- NIMBUS_AURORA_MAX_RETRIES (default 3)
- NIMBUS_AURORA_POOL_SIZE (default 16)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_AURORA_TIMEOUT_MS affects request timeout behavior for Aurora.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/aurora/restart
- GET /api/v1/aurora/status
- POST /api/v1/aurora/cache/flush
Use POST /api/v1/aurora/restart to restart the Aurora service, GET /api/v1/aurora/status to check health, and POST /api/v1/aurora/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Aurora service:
- ERR-1001: connection pool exhausted
- ERR-1002: upstream timeout exceeded
- ERR-1003: invalid authentication token
- ERR-1004: payload schema validation failed
When you see ERR-1001, the connection pool is exhausted; increase NIMBUS_AURORA_POOL_SIZE. ERR-1002 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Aurora service. If you observe connection drops or high latency, first check GET /api/v1/aurora/status, then review recent error codes. Restart with `nimbusctl aurora restart` or POST /api/v1/aurora/restart. Persistent timeouts usually mean NIMBUS_AURORA_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
