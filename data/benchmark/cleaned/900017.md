# Quartz Service

## Overview

The Quartz service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Quartz exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Quartz v2.6.0. Owner: SRE. This document describes configuration, endpoints, error codes, and troubleshooting for Quartz.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_QUARTZ_TIMEOUT_MS (default 3400)
- NIMBUS_QUARTZ_MAX_RETRIES (default 3)
- NIMBUS_QUARTZ_POOL_SIZE (default 16)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_QUARTZ_TIMEOUT_MS affects request timeout behavior for Quartz.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/quartz/restart
- GET /api/v1/quartz/status
- POST /api/v1/quartz/cache/flush
Use POST /api/v1/quartz/restart to restart the Quartz service, GET /api/v1/quartz/status to check health, and POST /api/v1/quartz/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Quartz service:
- ERR-1161: connection pool exhausted
- ERR-1162: upstream timeout exceeded
- ERR-1163: invalid authentication token
- ERR-1164: payload schema validation failed
When you see ERR-1161, the connection pool is exhausted; increase NIMBUS_QUARTZ_POOL_SIZE. ERR-1162 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Quartz service. If you observe connection drops or high latency, first check GET /api/v1/quartz/status, then review recent error codes. Restart with `nimbusctl quartz restart` or POST /api/v1/quartz/restart. Persistent timeouts usually mean NIMBUS_QUARTZ_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to SRE.
