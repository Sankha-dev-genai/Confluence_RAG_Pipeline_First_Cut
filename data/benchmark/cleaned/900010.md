# Jasper Service

## Overview

The Jasper service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Jasper exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Jasper v1.9.0. Owner: Infra Guild. This document describes configuration, endpoints, error codes, and troubleshooting for Jasper.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_JASPER_TIMEOUT_MS (default 3225)
- NIMBUS_JASPER_MAX_RETRIES (default 4)
- NIMBUS_JASPER_POOL_SIZE (default 20)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_JASPER_TIMEOUT_MS affects request timeout behavior for Jasper.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/jasper/restart
- GET /api/v1/jasper/status
- POST /api/v1/jasper/cache/flush
Use POST /api/v1/jasper/restart to restart the Jasper service, GET /api/v1/jasper/status to check health, and POST /api/v1/jasper/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Jasper service:
- ERR-1091: connection pool exhausted
- ERR-1092: upstream timeout exceeded
- ERR-1093: invalid authentication token
- ERR-1094: payload schema validation failed
When you see ERR-1091, the connection pool is exhausted; increase NIMBUS_JASPER_POOL_SIZE. ERR-1092 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Jasper service. If you observe connection drops or high latency, first check GET /api/v1/jasper/status, then review recent error codes. Restart with `nimbusctl jasper restart` or POST /api/v1/jasper/restart. Persistent timeouts usually mean NIMBUS_JASPER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Infra Guild.
