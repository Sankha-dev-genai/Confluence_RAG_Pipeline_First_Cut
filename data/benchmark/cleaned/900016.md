# Pyrite Service

## Overview

The Pyrite service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Pyrite exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Pyrite v1.5.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Pyrite.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_PYRITE_TIMEOUT_MS (default 3375)
- NIMBUS_PYRITE_MAX_RETRIES (default 6)
- NIMBUS_PYRITE_POOL_SIZE (default 44)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_PYRITE_TIMEOUT_MS affects request timeout behavior for Pyrite.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/pyrite/restart
- GET /api/v1/pyrite/status
- POST /api/v1/pyrite/cache/flush
Use POST /api/v1/pyrite/restart to restart the Pyrite service, GET /api/v1/pyrite/status to check health, and POST /api/v1/pyrite/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Pyrite service:
- ERR-1151: connection pool exhausted
- ERR-1152: upstream timeout exceeded
- ERR-1153: invalid authentication token
- ERR-1154: payload schema validation failed
When you see ERR-1151, the connection pool is exhausted; increase NIMBUS_PYRITE_POOL_SIZE. ERR-1152 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Pyrite service. If you observe connection drops or high latency, first check GET /api/v1/pyrite/status, then review recent error codes. Restart with `nimbusctl pyrite restart` or POST /api/v1/pyrite/restart. Persistent timeouts usually mean NIMBUS_PYRITE_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
