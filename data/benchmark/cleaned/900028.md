# Beryl Service

## Overview

The Beryl service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Beryl exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Beryl v1.7.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Beryl.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_BERYL_TIMEOUT_MS (default 3675)
- NIMBUS_BERYL_MAX_RETRIES (default 6)
- NIMBUS_BERYL_POOL_SIZE (default 28)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_BERYL_TIMEOUT_MS affects request timeout behavior for Beryl.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/beryl/restart
- GET /api/v1/beryl/status
- POST /api/v1/beryl/cache/flush
Use POST /api/v1/beryl/restart to restart the Beryl service, GET /api/v1/beryl/status to check health, and POST /api/v1/beryl/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Beryl service:
- ERR-1271: connection pool exhausted
- ERR-1272: upstream timeout exceeded
- ERR-1273: invalid authentication token
- ERR-1274: payload schema validation failed
When you see ERR-1271, the connection pool is exhausted; increase NIMBUS_BERYL_POOL_SIZE. ERR-1272 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Beryl service. If you observe connection drops or high latency, first check GET /api/v1/beryl/status, then review recent error codes. Restart with `nimbusctl beryl restart` or POST /api/v1/beryl/restart. Persistent timeouts usually mean NIMBUS_BERYL_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
