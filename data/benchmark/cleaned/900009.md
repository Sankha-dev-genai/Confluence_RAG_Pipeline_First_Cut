# Indigo Service

## Overview

The Indigo service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Indigo exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Indigo v3.8.0. Owner: Data Team. This document describes configuration, endpoints, error codes, and troubleshooting for Indigo.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_INDIGO_TIMEOUT_MS (default 3200)
- NIMBUS_INDIGO_MAX_RETRIES (default 3)
- NIMBUS_INDIGO_POOL_SIZE (default 16)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_INDIGO_TIMEOUT_MS affects request timeout behavior for Indigo.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/indigo/restart
- GET /api/v1/indigo/status
- POST /api/v1/indigo/cache/flush
Use POST /api/v1/indigo/restart to restart the Indigo service, GET /api/v1/indigo/status to check health, and POST /api/v1/indigo/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Indigo service:
- ERR-1081: connection pool exhausted
- ERR-1082: upstream timeout exceeded
- ERR-1083: invalid authentication token
- ERR-1084: payload schema validation failed
When you see ERR-1081, the connection pool is exhausted; increase NIMBUS_INDIGO_POOL_SIZE. ERR-1082 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Indigo service. If you observe connection drops or high latency, first check GET /api/v1/indigo/status, then review recent error codes. Restart with `nimbusctl indigo restart` or POST /api/v1/indigo/restart. Persistent timeouts usually mean NIMBUS_INDIGO_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Data Team.
