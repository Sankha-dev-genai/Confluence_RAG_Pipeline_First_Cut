# Xenon Service

## Overview

The Xenon service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Xenon exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Xenon v3.3.0. Owner: Data Team. This document describes configuration, endpoints, error codes, and troubleshooting for Xenon.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_XENON_TIMEOUT_MS (default 3575)
- NIMBUS_XENON_MAX_RETRIES (default 6)
- NIMBUS_XENON_POOL_SIZE (default 44)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_XENON_TIMEOUT_MS affects request timeout behavior for Xenon.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/xenon/restart
- GET /api/v1/xenon/status
- POST /api/v1/xenon/cache/flush
Use POST /api/v1/xenon/restart to restart the Xenon service, GET /api/v1/xenon/status to check health, and POST /api/v1/xenon/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Xenon service:
- ERR-1231: connection pool exhausted
- ERR-1232: upstream timeout exceeded
- ERR-1233: invalid authentication token
- ERR-1234: payload schema validation failed
When you see ERR-1231, the connection pool is exhausted; increase NIMBUS_XENON_POOL_SIZE. ERR-1232 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Xenon service. If you observe connection drops or high latency, first check GET /api/v1/xenon/status, then review recent error codes. Restart with `nimbusctl xenon restart` or POST /api/v1/xenon/restart. Persistent timeouts usually mean NIMBUS_XENON_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Data Team.
