# Kepler Service

## Overview

The Kepler service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Kepler exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Kepler v2.0.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Kepler.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_KEPLER_TIMEOUT_MS (default 3250)
- NIMBUS_KEPLER_MAX_RETRIES (default 5)
- NIMBUS_KEPLER_POOL_SIZE (default 24)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_KEPLER_TIMEOUT_MS affects request timeout behavior for Kepler.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/kepler/restart
- GET /api/v1/kepler/status
- POST /api/v1/kepler/cache/flush
Use POST /api/v1/kepler/restart to restart the Kepler service, GET /api/v1/kepler/status to check health, and POST /api/v1/kepler/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Kepler service:
- ERR-1101: connection pool exhausted
- ERR-1102: upstream timeout exceeded
- ERR-1103: invalid authentication token
- ERR-1104: payload schema validation failed
When you see ERR-1101, the connection pool is exhausted; increase NIMBUS_KEPLER_POOL_SIZE. ERR-1102 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Kepler service. If you observe connection drops or high latency, first check GET /api/v1/kepler/status, then review recent error codes. Restart with `nimbusctl kepler restart` or POST /api/v1/kepler/restart. Persistent timeouts usually mean NIMBUS_KEPLER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
