# Onyx Service

## Overview

The Onyx service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Onyx exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Onyx v3.4.0. Owner: Infra Guild. This document describes configuration, endpoints, error codes, and troubleshooting for Onyx.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_ONYX_TIMEOUT_MS (default 3350)
- NIMBUS_ONYX_MAX_RETRIES (default 5)
- NIMBUS_ONYX_POOL_SIZE (default 40)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_ONYX_TIMEOUT_MS affects request timeout behavior for Onyx.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/onyx/restart
- GET /api/v1/onyx/status
- POST /api/v1/onyx/cache/flush
Use POST /api/v1/onyx/restart to restart the Onyx service, GET /api/v1/onyx/status to check health, and POST /api/v1/onyx/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Onyx service:
- ERR-1141: connection pool exhausted
- ERR-1142: upstream timeout exceeded
- ERR-1143: invalid authentication token
- ERR-1144: payload schema validation failed
When you see ERR-1141, the connection pool is exhausted; increase NIMBUS_ONYX_POOL_SIZE. ERR-1142 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Onyx service. If you observe connection drops or high latency, first check GET /api/v1/onyx/status, then review recent error codes. Restart with `nimbusctl onyx restart` or POST /api/v1/onyx/restart. Persistent timeouts usually mean NIMBUS_ONYX_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Infra Guild.
