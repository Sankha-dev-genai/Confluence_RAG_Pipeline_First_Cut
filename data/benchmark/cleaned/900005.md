# Ember Service

## Overview

The Ember service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Ember exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Ember v2.4.0. Owner: Infra Guild. This document describes configuration, endpoints, error codes, and troubleshooting for Ember.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_EMBER_TIMEOUT_MS (default 3100)
- NIMBUS_EMBER_MAX_RETRIES (default 3)
- NIMBUS_EMBER_POOL_SIZE (default 32)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_EMBER_TIMEOUT_MS affects request timeout behavior for Ember.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/ember/restart
- GET /api/v1/ember/status
- POST /api/v1/ember/cache/flush
Use POST /api/v1/ember/restart to restart the Ember service, GET /api/v1/ember/status to check health, and POST /api/v1/ember/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Ember service:
- ERR-1041: connection pool exhausted
- ERR-1042: upstream timeout exceeded
- ERR-1043: invalid authentication token
- ERR-1044: payload schema validation failed
When you see ERR-1041, the connection pool is exhausted; increase NIMBUS_EMBER_POOL_SIZE. ERR-1042 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Ember service. If you observe connection drops or high latency, first check GET /api/v1/ember/status, then review recent error codes. Restart with `nimbusctl ember restart` or POST /api/v1/ember/restart. Persistent timeouts usually mean NIMBUS_EMBER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Infra Guild.
