# Cobalt Service

## Overview

The Cobalt service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Cobalt exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Cobalt v3.2.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Cobalt.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_COBALT_TIMEOUT_MS (default 3050)
- NIMBUS_COBALT_MAX_RETRIES (default 5)
- NIMBUS_COBALT_POOL_SIZE (default 24)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_COBALT_TIMEOUT_MS affects request timeout behavior for Cobalt.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/cobalt/restart
- GET /api/v1/cobalt/status
- POST /api/v1/cobalt/cache/flush
Use POST /api/v1/cobalt/restart to restart the Cobalt service, GET /api/v1/cobalt/status to check health, and POST /api/v1/cobalt/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Cobalt service:
- ERR-1021: connection pool exhausted
- ERR-1022: upstream timeout exceeded
- ERR-1023: invalid authentication token
- ERR-1024: payload schema validation failed
When you see ERR-1021, the connection pool is exhausted; increase NIMBUS_COBALT_POOL_SIZE. ERR-1022 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Cobalt service. If you observe connection drops or high latency, first check GET /api/v1/cobalt/status, then review recent error codes. Restart with `nimbusctl cobalt restart` or POST /api/v1/cobalt/restart. Persistent timeouts usually mean NIMBUS_COBALT_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
