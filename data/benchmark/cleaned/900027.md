# Amber Service

## Overview

The Amber service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Amber exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Amber v3.6.0. Owner: SRE. This document describes configuration, endpoints, error codes, and troubleshooting for Amber.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_AMBER_TIMEOUT_MS (default 3650)
- NIMBUS_AMBER_MAX_RETRIES (default 5)
- NIMBUS_AMBER_POOL_SIZE (default 24)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_AMBER_TIMEOUT_MS affects request timeout behavior for Amber.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/amber/restart
- GET /api/v1/amber/status
- POST /api/v1/amber/cache/flush
Use POST /api/v1/amber/restart to restart the Amber service, GET /api/v1/amber/status to check health, and POST /api/v1/amber/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Amber service:
- ERR-1261: connection pool exhausted
- ERR-1262: upstream timeout exceeded
- ERR-1263: invalid authentication token
- ERR-1264: payload schema validation failed
When you see ERR-1261, the connection pool is exhausted; increase NIMBUS_AMBER_POOL_SIZE. ERR-1262 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Amber service. If you observe connection drops or high latency, first check GET /api/v1/amber/status, then review recent error codes. Restart with `nimbusctl amber restart` or POST /api/v1/amber/restart. Persistent timeouts usually mean NIMBUS_AMBER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to SRE.
