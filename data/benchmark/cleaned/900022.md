# Verdant Service

## Overview

The Verdant service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Verdant exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Verdant v1.1.0. Owner: SRE. This document describes configuration, endpoints, error codes, and troubleshooting for Verdant.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_VERDANT_TIMEOUT_MS (default 3525)
- NIMBUS_VERDANT_MAX_RETRIES (default 4)
- NIMBUS_VERDANT_POOL_SIZE (default 36)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_VERDANT_TIMEOUT_MS affects request timeout behavior for Verdant.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/verdant/restart
- GET /api/v1/verdant/status
- POST /api/v1/verdant/cache/flush
Use POST /api/v1/verdant/restart to restart the Verdant service, GET /api/v1/verdant/status to check health, and POST /api/v1/verdant/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Verdant service:
- ERR-1211: connection pool exhausted
- ERR-1212: upstream timeout exceeded
- ERR-1213: invalid authentication token
- ERR-1214: payload schema validation failed
When you see ERR-1211, the connection pool is exhausted; increase NIMBUS_VERDANT_POOL_SIZE. ERR-1212 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Verdant service. If you observe connection drops or high latency, first check GET /api/v1/verdant/status, then review recent error codes. Restart with `nimbusctl verdant restart` or POST /api/v1/verdant/restart. Persistent timeouts usually mean NIMBUS_VERDANT_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to SRE.
