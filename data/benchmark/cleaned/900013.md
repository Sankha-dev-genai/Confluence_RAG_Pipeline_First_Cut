# Marble Service

## Overview

The Marble service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Marble exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Marble v1.2.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Marble.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_MARBLE_TIMEOUT_MS (default 3300)
- NIMBUS_MARBLE_MAX_RETRIES (default 3)
- NIMBUS_MARBLE_POOL_SIZE (default 32)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_MARBLE_TIMEOUT_MS affects request timeout behavior for Marble.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/marble/restart
- GET /api/v1/marble/status
- POST /api/v1/marble/cache/flush
Use POST /api/v1/marble/restart to restart the Marble service, GET /api/v1/marble/status to check health, and POST /api/v1/marble/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Marble service:
- ERR-1121: connection pool exhausted
- ERR-1122: upstream timeout exceeded
- ERR-1123: invalid authentication token
- ERR-1124: payload schema validation failed
When you see ERR-1121, the connection pool is exhausted; increase NIMBUS_MARBLE_POOL_SIZE. ERR-1122 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Marble service. If you observe connection drops or high latency, first check GET /api/v1/marble/status, then review recent error codes. Restart with `nimbusctl marble restart` or POST /api/v1/marble/restart. Persistent timeouts usually mean NIMBUS_MARBLE_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
