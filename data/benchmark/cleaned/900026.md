# Zephyr Service

## Overview

The Zephyr service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Zephyr exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Zephyr v2.5.0. Owner: Platform Team. This document describes configuration, endpoints, error codes, and troubleshooting for Zephyr.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_ZEPHYR_TIMEOUT_MS (default 3625)
- NIMBUS_ZEPHYR_MAX_RETRIES (default 4)
- NIMBUS_ZEPHYR_POOL_SIZE (default 20)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_ZEPHYR_TIMEOUT_MS affects request timeout behavior for Zephyr.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/zephyr/restart
- GET /api/v1/zephyr/status
- POST /api/v1/zephyr/cache/flush
Use POST /api/v1/zephyr/restart to restart the Zephyr service, GET /api/v1/zephyr/status to check health, and POST /api/v1/zephyr/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Zephyr service:
- ERR-1251: connection pool exhausted
- ERR-1252: upstream timeout exceeded
- ERR-1253: invalid authentication token
- ERR-1254: payload schema validation failed
When you see ERR-1251, the connection pool is exhausted; increase NIMBUS_ZEPHYR_POOL_SIZE. ERR-1252 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Zephyr service. If you observe connection drops or high latency, first check GET /api/v1/zephyr/status, then review recent error codes. Restart with `nimbusctl zephyr restart` or POST /api/v1/zephyr/restart. Persistent timeouts usually mean NIMBUS_ZEPHYR_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to Platform Team.
