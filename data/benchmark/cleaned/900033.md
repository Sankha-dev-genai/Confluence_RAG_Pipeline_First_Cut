# Glacier Service

## Overview

The Glacier service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Glacier exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Glacier v3.2.0. Owner: API Team. This document describes configuration, endpoints, error codes, and troubleshooting for Glacier.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_GLACIER_TIMEOUT_MS (default 3800)
- NIMBUS_GLACIER_MAX_RETRIES (default 3)
- NIMBUS_GLACIER_POOL_SIZE (default 16)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_GLACIER_TIMEOUT_MS affects request timeout behavior for Glacier.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/glacier/restart
- GET /api/v1/glacier/status
- POST /api/v1/glacier/cache/flush
Use POST /api/v1/glacier/restart to restart the Glacier service, GET /api/v1/glacier/status to check health, and POST /api/v1/glacier/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Glacier service:
- ERR-1321: connection pool exhausted
- ERR-1322: upstream timeout exceeded
- ERR-1323: invalid authentication token
- ERR-1324: payload schema validation failed
When you see ERR-1321, the connection pool is exhausted; increase NIMBUS_GLACIER_POOL_SIZE. ERR-1322 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Glacier service. If you observe connection drops or high latency, first check GET /api/v1/glacier/status, then review recent error codes. Restart with `nimbusctl glacier restart` or POST /api/v1/glacier/restart. Persistent timeouts usually mean NIMBUS_GLACIER_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to API Team.
