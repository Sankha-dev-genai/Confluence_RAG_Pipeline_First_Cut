# Granite Service

## Overview

The Granite service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Granite exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Granite v1.6.0. Owner: SRE. This document describes configuration, endpoints, error codes, and troubleshooting for Granite.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_GRANITE_TIMEOUT_MS (default 3150)
- NIMBUS_GRANITE_MAX_RETRIES (default 5)
- NIMBUS_GRANITE_POOL_SIZE (default 40)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_GRANITE_TIMEOUT_MS affects request timeout behavior for Granite.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/granite/restart
- GET /api/v1/granite/status
- POST /api/v1/granite/cache/flush
Use POST /api/v1/granite/restart to restart the Granite service, GET /api/v1/granite/status to check health, and POST /api/v1/granite/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Granite service:
- ERR-1061: connection pool exhausted
- ERR-1062: upstream timeout exceeded
- ERR-1063: invalid authentication token
- ERR-1064: payload schema validation failed
When you see ERR-1061, the connection pool is exhausted; increase NIMBUS_GRANITE_POOL_SIZE. ERR-1062 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Granite service. If you observe connection drops or high latency, first check GET /api/v1/granite/status, then review recent error codes. Restart with `nimbusctl granite restart` or POST /api/v1/granite/restart. Persistent timeouts usually mean NIMBUS_GRANITE_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to SRE.
