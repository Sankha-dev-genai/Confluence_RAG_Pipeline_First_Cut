# Basalt Service

## Overview

The Basalt service is a component of the Nimbus platform responsible for handling requests reliably and at high throughput. It provides horizontal scalability, health checks, and graceful degradation under load. Like other Nimbus services, Basalt exposes metrics, supports rolling restarts, and integrates with the shared observability stack. Current version: Basalt v2.1.0. Owner: SRE. This document describes configuration, endpoints, error codes, and troubleshooting for Basalt.

## Configuration

Configuration keys and defaults for the service:
- NIMBUS_BASALT_TIMEOUT_MS (default 3025)
- NIMBUS_BASALT_MAX_RETRIES (default 4)
- NIMBUS_BASALT_POOL_SIZE (default 20)
Each key can be overridden via environment variable or the nimbus.yaml file. Changing NIMBUS_BASALT_TIMEOUT_MS affects request timeout behavior for Basalt.

## API Endpoints

HTTP endpoints exposed by the service:
- POST /api/v1/basalt/restart
- GET /api/v1/basalt/status
- POST /api/v1/basalt/cache/flush
Use POST /api/v1/basalt/restart to restart the Basalt service, GET /api/v1/basalt/status to check health, and POST /api/v1/basalt/cache/flush to clear its cache.

## Error Codes

Error codes emitted by the Basalt service:
- ERR-1011: connection pool exhausted
- ERR-1012: upstream timeout exceeded
- ERR-1013: invalid authentication token
- ERR-1014: payload schema validation failed
When you see ERR-1011, the connection pool is exhausted; increase NIMBUS_BASALT_POOL_SIZE. ERR-1012 indicates an upstream timeout.

## Troubleshooting

Troubleshooting the Basalt service. If you observe connection drops or high latency, first check GET /api/v1/basalt/status, then review recent error codes. Restart with `nimbusctl basalt restart` or POST /api/v1/basalt/restart. Persistent timeouts usually mean NIMBUS_BASALT_TIMEOUT_MS is set too low. As with all Nimbus services, verify upstream health and inspect the shared dashboards before escalating to SRE.
