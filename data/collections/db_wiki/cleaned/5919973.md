**Bigtable** is a fully managed [wide-column](/wiki/Wide-column_store "Wide-column store") and [key-value](/wiki/Key-value "Key-value") [NoSQL](/wiki/NoSQL "NoSQL") database service for large analytical and operational workloads as part of the [Google Cloud](/wiki/Google_Cloud "Google Cloud") portfolio.

## History

Bigtable development began in 2004.[[1]](#cite_note-1) It is now used by a number of Google applications, such as [Google Analytics](/wiki/Google_Analytics "Google Analytics"),[[2]](#cite_note-:0-2) web indexing,[[3]](#cite_note-FOOTNOTEChangDeanGhemawatHsieh2006-3) [MapReduce](/wiki/MapReduce "MapReduce"), which is often used for generating and modifying data stored in Bigtable,[[4]](#cite_note-FOOTNOTEChangDeanGhemawatHsieh20063-4) [Google Maps](/wiki/Google_Maps "Google Maps"),[[5]](#cite_note-5) [Google Books](/wiki/Google_Books "Google Books") search, "My Search History", [Google Earth](/wiki/Google_Earth "Google Earth"), [Blogger.com](/wiki/Blogger.com "Blogger.com"), [Google Code](/wiki/Google_Code "Google Code") hosting, [YouTube](/wiki/YouTube "YouTube"),[[6]](#cite_note-6) and [Gmail](/wiki/Gmail "Gmail").[[7]](#cite_note-7) Google's reasons for developing its own database include scalability and better control of performance characteristics.[[8]](#cite_note-FOOTNOTEChangDeanGhemawatHsieh2006Conclusion-8)

[Apache HBase](/wiki/Apache_HBase "Apache HBase") and [Cassandra](/wiki/Apache_Cassandra "Apache Cassandra") are some of the best known open source projects that were modeled after Bigtable. Bigtable offers [HBase](https://cloud.google.com/bigtable/docs/hbase-bigtable) and [Cassandra compatible APIs](https://cloud.google.com/bigtable/docs/migrate-from-cassandra).

On 6 May 2015, a public version of Bigtable was made available as a part of [Google Cloud](/wiki/Google_Cloud_Platform "Google Cloud Platform") under the name Cloud Bigtable.**[[2]](#cite_note-:0-2)**

As of April 2024, Bigtable manages over 10 Exabytes of data and serves more than 7 billion requests per second.[[9]](#cite_note-9) Since its launch, Google announced a number of updates to Bigtable, including [SQL support](https://cloud.google.com/bigtable/docs/googlesql-overview), [incremental materialized views](https://cloud.google.com/bigtable/docs/continuous-materialized-views), [global secondary indexes](https://cloud.google.com/bigtable/docs/global-secondary-index) and automated scalability.[[10]](#cite_note-10)

## Design

Bigtable is one of the prototypical examples of a [wide-column store](/wiki/Wide-column_store "Wide-column store"). It maps two arbitrary string values (row key and column key) and timestamp (hence three-dimensional mapping) into an associated arbitrary byte array. It is not a relational database and can be better defined as a sparse, distributed multi-dimensional sorted map.[[3]](#cite_note-FOOTNOTEChangDeanGhemawatHsieh2006-3): 1 It is built on Colossus ([Google File System](/wiki/Google_File_System "Google File System")), [Chubby Lock Service](/wiki/Distributed_lock_manager#Other_implementations "Distributed lock manager"), SSTable (log-structured storage like [LevelDB](/wiki/LevelDB "LevelDB")) and a few other [Google](/wiki/Google "Google") technologies. Bigtable is designed to scale into the [petabyte](/wiki/Petabyte "Petabyte") range across "hundreds or thousands of machines, and to make it easy to add more machines [to] the system and automatically start taking advantage of those resources without any reconfiguration".[[11]](#cite_note-o'reilly-11) For example, Google's copy of the web can be stored in a bigtable where the row key is a [domain-reversed URL](/wiki/Reverse_domain_name_notation "Reverse domain name notation"), and columns describe various properties of a web page, with one particular column holding the page itself. The page column can have several timestamped versions describing different copies of the web page timestamped by when they were fetched. Each cell of a bigtable can have zero or more timestamped versions of the data. Another function of the timestamp is to allow for both [versioning](/wiki/Version_control "Version control") and [garbage collection](/wiki/Garbage_collection_(computer_science) "Garbage collection (computer science)") of expired data.

Tables are split into multiple *tablets* – segments of the table are split at certain row keys so that each tablet is a few hundred megabytes or a few gigabytes in size. A bigtable is somewhat like a mapreduce worker pool in that thousands to hundreds of thousands of tablet shards may be served by hundreds to thousands of BigTable servers. When Table size threaten to grow beyond a specified limit, the tablets may be compressed using the algorithm BMDiff[[12]](#cite_note-algorithms1-12)[[13]](#cite_note-13) and the Zippy compression algorithm[[14]](#cite_note-algorithms2-14) publicly known and open-sourced as [Snappy](/wiki/Snappy_(compression) "Snappy (compression)"),[[15]](#cite_note-15) which is a less space-optimal variation of [LZ77](/wiki/LZ77 "LZ77") but more efficient in terms of computing time. The locations in the GFS of tablets are recorded as database entries in multiple special tablets, which are called "META1" tablets. META1 tablets are found by querying the single "META0" tablet, which typically resides on a server of its own since it is often queried by clients as to the location of the "META1" tablet which itself has the answer to the question of where the actual data is located. Like GFS's master server, the META0 server is not generally a [bottleneck](/wiki/Bottleneck_(software) "Bottleneck (software)") since the processor time and bandwidth necessary to discover and transmit META1 locations is minimal and clients aggressively cache locations to minimize queries.
